# Архитектура NexTalk

NexTalk - учебный клиент-серверный мессенджер на C++ для UNIX/POSIX-систем.
Проект специально построен вокруг низкоуровневых TCP-сокетов, собственного
прикладного протокола, многопоточности и постоянного хранения истории сообщений.

## Модули проекта

- `client/` - клиентская часть. Содержит консольный клиент, общий клиентский
  сетевой слой и опциональный Qt Widgets frontend.
- `server/` - TCP-сервер. Принимает подключения, хранит онлайн-сессии,
  маршрутизирует личные сообщения, пишет логи и работает с SQLite.
- `common/` - общий код протокола. Здесь находятся типы команд, сериализация и
  парсинг сообщений.
- `ai_service/` - Python-заготовка AI-сервиса для будущего анализа вложений.
- `docs/` - документация по архитектуре, протоколу и ходу разработки.

Главная идея разделения: клиент и сервер используют один общий формат
сообщений из `common`, но бизнес-логика клиента, сервера, хранилища и
пользовательского интерфейса не смешивается между собой.

## Клиентский UI-слой

Клиентская сетевая логика вынесена в `client::ClientConnection`. Этот класс не
зависит от Qt, консоли или другого конкретного интерфейса. Он отвечает за:

- подключение к серверу;
- отправку `login`, `send_message`, `fetch_history`, `fetch_chats`,
  `search_users`, `create_chat`, `quit`;
- запуск receiver thread;
- разбор входящих сообщений сервера;
- вызов typed callbacks для UI-слоя.

Консольный клиент использует `ClientConnection` и только отображает события в
терминале. Qt-клиент также строится поверх `ClientConnection`, но находится в
отдельной директории `client/src/qt`.

Такой подход оставляет возможность заменить GUI в будущем: например, добавить
веб-интерфейс, TUI или другой desktop frontend без переписывания протокола и
сетевого кода.

## Сетевой слой

Клиент и сервер общаются поверх TCP. Сервер использует POSIX-сокеты:

- `socket` - создает listening socket;
- `setsockopt` с `SO_REUSEADDR` - позволяет быстро перезапускать сервер на том
  же порту;
- `bind` - привязывает сервер к IP-адресу и порту;
- `listen` - переводит socket в режим ожидания подключений;
- `select` - ждет входящие подключения с таймаутом;
- `accept` - принимает нового клиента и создает socket конкретной сессии;
- `recv` - читает данные клиента;
- `send` - отправляет данные клиенту;
- `shutdown` и `close` - корректно закрывают соединения.

Локальный режим запускается через `127.0.0.1`. Сетевой режим запускается через
`0.0.0.0` на сервере и подключение клиента к IP-адресу машины с сервером.

## Прикладной протокол

Протокол текстовый и работает поверх TCP. Одно протокольное сообщение занимает
одну строку:

```text
command<TAB>field1<TAB>field2\n
```

TCP передает поток байтов, а не готовые сообщения, поэтому границей сообщения
выбран символ `\n`.

Поддержанные команды клиента:

- `login` - вход или смена имени пользователя;
- `register` - создание аккаунта с паролем;
- `send_message` - личное сообщение другому онлайн-пользователю;
- `fetch_history` - запрос истории личного диалога;
- `fetch_chats` - запрос списка диалогов;
- `search_users` - поиск пользователей по части имени; сервер исключает уже
  существующие диалоги через id пользователей;
- `create_chat` - создание пустого личного диалога по id пользователя;
- `quit` - завершение сессии.

Ответы и события сервера:

- `login_result` - результат входа;
- `register_result` - результат регистрации;
- `incoming_message` - входящее личное сообщение;
- `history_message` - одна запись из истории;
- `history_result` - завершение выдачи истории;
- `chat_item` - один диалог в списке чатов;
- `chat_list_result` - завершение выдачи списка чатов;
- `user_search_item` / `user_search_result` - выдача результатов поиска;
- `create_chat_result` - результат создания пустого диалога;
- `info` - информационное сообщение;
- `error` - ошибка.

Поля экранируются, чтобы пользовательский текст не ломал формат протокола:

```text
\   -> \\
TAB -> \t
\n  -> \n
\r  -> \r
```

Подробное описание протокола находится в `docs/protocol.md`.

## Модель многопоточности

Сервер использует модель "один клиент - один поток". Главный поток сервера
принимает подключения, а для каждой подключенной сессии запускается отдельный
`std::thread`.

Поток клиента на сервере:

1. читает строки протокола через `recv`;
2. парсит их через `common::parseMessage`;
3. обрабатывает команду;
4. отправляет ответ через `sendAll`.

Клиент тоже многопоточный:

- главный поток читает команды пользователя из консоли;
- receiver thread читает входящие сообщения от сервера и печатает их сразу.

Такая схема позволяет получать сообщения, даже если пользователь ничего не
вводит.

## Синхронизация потоков

Общие данные защищены синхронизацией:

- `clientsMutex_` защищает таблицу онлайн-пользователей;
- `sessionsMutex_` защищает список всех клиентских сессий;
- `threadsMutex_` защищает список worker-потоков;
- `logMutex_` защищает запись в лог-файл;
- `ClientSession::writeMutex` защищает запись в socket конкретного клиента;
- `MessageStore` использует свой `mutex` вокруг SQLite;
- `std::atomic<bool>` используется для флагов работы сервера и активности
  сессий.

Это важно, потому что несколько клиентских потоков могут одновременно читать
таблицу пользователей, писать в лог или отправлять события одному и тому же
пользователю.

## Хранение данных SQLite

SQLite вынесен в отдельный класс `MessageStore`. Сервер не формирует SQL-запросы
напрямую в обработчиках команд, а вызывает методы хранилища:

- `ensureUser` - сохранить пользователя, если его еще нет;
- `saveMessage` - сохранить доставленное личное сообщение;
- `fetchHistory` - загрузить последние сообщения личного диалога.

База содержит три таблицы:

### users

Хранит известных пользователей.

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
username TEXT NOT NULL UNIQUE
password_salt TEXT
password_hash TEXT
created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
```

### conversations

Хранит личные диалоги между двумя пользователями.

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
user_low TEXT NOT NULL
user_high TEXT NOT NULL
created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
UNIQUE(user_low, user_high)
```

Пара пользователей хранится в отсортированном виде, чтобы диалоги `alice-bob` и
`bob-alice` не создавали две разные записи.

### messages

Хранит доставленные сообщения.

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
conversation_id INTEGER NOT NULL
sender TEXT NOT NULL
recipient TEXT NOT NULL
body TEXT NOT NULL
created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
FOREIGN KEY(conversation_id) REFERENCES conversations(id)
```

Сообщения сохраняются в SQLite до попытки online-доставки. Если получатель
offline, сообщение остается доступным в истории и появится в списке чатов после
следующего входа пользователя.

## Логи и завершение

Сервер пишет события в лог-файл в append-режиме. Логи сохраняются между
запусками.

Логируются:

- запуск и остановка сервера;
- подключение и отключение клиента;
- логин пользователя;
- получение сообщения сервером;
- успешная доставка;
- ошибки доставки;
- запросы истории.

Сервер обрабатывает `SIGINT` и `SIGTERM`. Обработчик сигнала только выставляет
флаг остановки, а реальное завершение выполняется в основном цикле. Также
игнорируется `SIGPIPE`, чтобы сервер не падал при записи в закрытый socket.

## Расширяемость

Текущая архитектура оставляет несколько понятных точек расширения:

- Qt GUI и другие интерфейсы можно строить поверх `ClientConnection`;
- веб-интерфейс можно добавить как отдельный frontend, который переиспользует
  сетевой слой или общается с сервером через адаптер;
- групповые чаты можно добавить через новые таблицы и команды протокола;
- ответы, пересылки и треды можно добавить через `message_id` и дополнительные
  поля сообщений;
- TLS/OpenSSL можно добавить на сетевом уровне, не меняя смысл команд
  протокола;
- offline-доставку можно реализовать через статусы сообщений в SQLite;
- локальный кэш клиента можно добавить отдельно от серверной истории.

## Следующие этапы

1. Вынести клиентский сетевой слой в отдельный класс.
2. Перейти к Qt GUI поверх готового сетевого слоя.
3. Добавить TLS/OpenSSL для шифрования транспорта.
4. Подключить вложения.
5. Подключить AI-анализ вложений через сервер.
6. Расширить тестовое покрытие сетевых сценариев.
