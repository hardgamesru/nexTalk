# Архитектура NexTalk

## 1. Цель проекта

NexTalk - учебный мессенджер с личными сообщениями, рассчитанный на:

- локальный запуск на одной машине;
- сетевой запуск между разными машинами/VM;
- сохранение истории и системных логов;
- дальнейшее расширение (шифрование, delivery guarantees, треды).

## 2. Модульная структура

- `common/`
  - общий прикладной протокол;
  - сериализация/десериализация команд.
- `server/`
  - TCP server;
  - маршрутизация сообщений;
  - авторизация;
  - работа с SQLite;
  - логирование.
- `client/`
  - `ClientConnection` (UI-agnostic сетевой слой);
  - консольный интерфейс;
  - опциональный Qt интерфейс.
- `web/`
  - Vue + Vite frontend;
  - WebSocket bridge к TLS-серверу.

Разделение `common`/`server`/`client` исключает дублирование формата команд и
упрощает поддержку.

## 3. Серверная модель

### 3.1 Сеть и системные вызовы

Сервер использует POSIX API:

- `socket`
- `setsockopt(SO_REUSEADDR)`
- `bind`
- `listen`
- `select`
- `accept`
- `recv`
- `send`
- `shutdown`
- `close`

Поверх принятого TCP-сокета сервер поднимает TLS-сессию через OpenSSL:

- `TLS_server_method`
- `SSL_CTX_new`
- `SSL_new`
- `SSL_set_fd`
- `SSL_accept`
- `SSL_read`
- `SSL_write`
- `SSL_free`
- `SSL_CTX_free`

### 3.2 Многопоточность

- Главный поток принимает подключения.
- На каждую клиентскую сессию создается отдельный worker thread.

Это обеспечивает параллельную работу нескольких клиентов и упрощает логику
обработки сессий.

### 3.3 Синхронизация

Используются:

- `clientsMutex_` - карта онлайн-пользователей;
- `sessionsMutex_` - список активных сессий;
- `threadsMutex_` - список worker-потоков;
- `logMutex_` - запись в лог;
- `ClientSession::writeMutex` - конкурентная отправка в один socket;
- mutex в `MessageStore` - сериализация SQL-операций;
- `std::atomic<bool>` - флаги жизненного цикла.

## 4. Клиентская часть

### 4.1 C++ клиент

`client::ClientConnection` инкапсулирует:

- подключение к серверу;
- отправку команд;
- receiver loop в отдельном потоке;
- dispatch ответов в callbacks.

Интерфейсы (CLI/Qt) используют один и тот же сетевой слой.

### 4.2 Web клиент

Браузер не может открыть raw TCP socket напрямую, поэтому используется bridge:

- браузер <-> bridge: WebSocket;
- bridge <-> сервер: TLS поверх TCP.

Bridge находится в `web/bridge/server.mjs` и прозрачно проксирует протокольные
строки.

При этом прикладной протокол не меняется: строки `command<TAB>...` остаются
теми же. TLS добавлен только как транспортный слой между Node.js bridge и C++
сервером.

Web-клиент хранит только состояние текущей сессии: выбранный чат, текст в
поле ввода, список сообщений, список чатов и строки session log. 

Профили пользователей живут отдельным слоем поверх истории сообщений. Сообщение
по-прежнему хранит только `sender`/`username`, а frontend уже во время
отрисовки подставляет `displayName`, цвет аватарки и initials из отдельного
словаря профилей. Это позволяет обновлять имя пользователя без миграции старых
сообщений и без переписывания IndexedDB-кэша.

После входа web-клиент не выбирает первый чат автоматически. Вместо этого он
показывает пустой экран с приглашением выбрать диалог. 

Для выбора чата используется стабильный `peerId`. В личном диалоге это username
собеседника, а в группе - строка вида `group:<id>`. Это важно для frontend:
название группы может измениться, но `peerId` остается тем же.

Для ускорения повторного открытия чатов frontend теперь использует два слоя
хранения сообщений:

- RAM (`messagesByPeer`) - рабочее состояние текущей сессии;
- IndexedDB - локальный persistent-кэш последних сообщений.

При открытии чата клиент сначала читает последние сообщения из IndexedDB,
кладет их в RAM и показывает их сразу. Затем он отправляет `fetch_history` на
сервер, чтобы синхронизировать хвост с источником истины. Более старые
сообщения, загруженные через прокрутку вверх, сохраняются только в RAM и не
пишутся в IndexedDB.

Отдельно от обычных диалогов в web-клиенте живет виртуальный чат `NexTalk AI`.
Он не создается на C++ сервере, не попадает в серверную SQLite-историю и не
участвует в unread-логике обычных переписок. Для него используется отдельный
путь:

- Vue frontend -> `ai_service` -> provider -> Ollama.

AI-история тоже кэшируется локально, но отдельно от обычных сообщений: в своем
IndexedDB-store на пользователя. Это позволяет сохранять контекст AI-диалога
между сессиями, не смешивая его с `messagesByPeer` и серверной историей.

Поверх полного AI-чата добавлен быстрый сценарий `AI Reply`. Он использует тот
же `ai_service`, но работает как одноразовая генерация ответа для текущего
чата: без переключения в `NexTalk AI`, без сохранения в AI-историю и без
автоматической отправки сообщения в основной диалог.

## 5. Модель данных SQLite

Основные таблицы:

- `users`
  - учетные записи (username + salt/hash), а также поля профиля:
    `display_name`, `bio`, `avatar_color`, `created_at`, `last_seen`.
- `conversations`
  - уникальные пары пользователей (`user_low`, `user_high`).
- `messages`
  - сообщения личных диалогов, включая `reply_to_message_id` и
    `forward_from_message_id`, а также поля мягкого удаления
    `deleted_at` и `deleted_by`.
- `conversation_reads`
  - последняя прочитанная позиция для `(conversation_id, username)`.
- `groups_chat`
  - групповые чаты, название и администратор.
- `group_members`
  - участники групп.
- `group_messages`
  - сообщения групп, включая ответы, пересылку, мягкое удаление и системные
    сообщения.
- `group_reads`
  - последняя прочитанная позиция в группе для конкретного пользователя.

Флаг `online` намеренно не хранится в SQLite. Он вычисляется сервером по
текущему состоянию подключений (`onlineUsers_`), а в базе остается только
`last_seen`, который переживает перезапуск сервера и logout пользователя.


## 6. Поток обработки сообщений

1. Клиент отправляет `send_message`.
2. Сервер валидирует пользователя и собеседника.
3. Сообщение сохраняется в SQLite.
4. Если получатель online - сервер отправляет `incoming_message`.
5. При запросе чатов сервер считает `unread_count` и возвращает в `chat_item`.
6. Когда чат открыт, клиент отправляет `mark_read`, сервер обновляет
   `conversation_reads`.

Для активного открытого чата входящее сообщение сразу помечается прочитанным:
клиент получает `incoming_message`, отображает его в текущей переписке и
отправляет `mark_read`. Для неактивного чата серверный `unread_count` остается
больше нуля, и frontend показывает красную точку в списке чатов.

Для групп используется тот же внешний поток команд, но другая таблица хранения:
`group_messages` вместо `messages` и `group_reads` вместо
`conversation_reads`. Благодаря этому личные диалоги не смешиваются с логикой
участников и администратора группы.

Ответы и пересылки строятся вокруг постоянного `message_id`. Сервер отдает его
в `send_message_result`, `incoming_message` и `history_message`, поэтому
frontend может безопасно показать цитату, открыть пересланное сообщение или
прокрутить историю к исходному сообщению.

Мягкое удаление не выбрасывает сообщение из истории. Сервер обновляет уже
существующую запись по `message_id`, выставляет `deleted_at` и `deleted_by`, а
frontend заменяет исходный текст на строку "Сообщение удалено". Благодаря
этому порядок истории, локальный кэш и ссылки reply/forward не ломаются.

Для удаления сообщений в группах важен не только `message_id`, но и контекст
чата. Числовые id в таблицах `messages` и `group_messages` независимы и могут
совпадать, поэтому команда удаления теперь передает `chat_id` вместе с
`message_id`. Сервер использует эту пару, чтобы однозначно понять, из какой
таблицы и из какой конкретно переписки нужно пометить сообщение удаленным.

Для подгрузки истории вверх используется отдельная команда
`fetch_history_before`. Она принимает `chat_id`, `before_message_id` и `limit`,
а сервер возвращает сообщения старше указанного id. Клиент добавляет их в
начало массива в RAM и восстанавливает позицию scroll, чтобы окно переписки не
прыгало.

## 7. Логи и сигналы

### 7.1 Логи

Лог-файл ведется в append-режиме и сохраняется между сессиями.
Событие старта сервера дополнительно фиксирует, что транспорт запущен в режиме
`tls=enabled`.

### 7.2 Сигналы

Сервер обрабатывает:

- `SIGINT`
- `SIGTERM`
- `SIGPIPE` (игнорируется)

Обработчик сигнала только выставляет флаг остановки; фактический shutdown идет
в нормальном контексте main loop.

## 8. Расширяемость

Точки расширения уже заложены:

- новые типы чатов через стабильный `chat_id`;
- треды через дополнительную ссылку на корневое сообщение;
- увеличение локального кэша сообщений через замену policy в IndexedDB;
- замена AI-провайдера через abstraction в `ai_service` без переписывания web UI;
- шифрование транспорта (TLS/OpenSSL) на сетевом уровне;
- последующая замена self-signed dev-сертификата на нормальный certificate chain;
- подтверждение доставки (acked/unacked + retry queue);
- многоплатформенные фронтенды поверх текущего протокола.
