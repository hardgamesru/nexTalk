# Архитектура NexTalk

## 1. Цель проекта

NexTalk - учебный мессенджер с личными сообщениями, рассчитанный на:

- локальный запуск на одной машине;
- сетевой запуск между разными машинами/VM;
- сохранение истории и системных логов;
- дальнейшее расширение (шифрование, delivery guarantees, треды).

## 2. Модульная структура

- `common/`
  - общий прикладной протокол;
  - сериализация/десериализация команд.
- `server/`
  - TCP server;
  - маршрутизация сообщений;
  - авторизация;
  - работа с SQLite;
  - логирование.
- `client/`
  - `ClientConnection` (UI-agnostic сетевой слой);
  - консольный интерфейс;
  - опциональный Qt интерфейс.
- `web/`
  - Vue + Vite frontend;
  - WebSocket bridge к TCP серверу.

Разделение `common`/`server`/`client` исключает дублирование формата команд и
упрощает поддержку.

## 3. Серверная модель

### 3.1 Сеть и системные вызовы

Сервер использует POSIX API:

- `socket`
- `setsockopt(SO_REUSEADDR)`
- `bind`
- `listen`
- `select`
- `accept`
- `recv`
- `send`
- `shutdown`
- `close`

### 3.2 Многопоточность

- Главный поток принимает подключения.
- На каждую клиентскую сессию создается отдельный worker thread.

Это обеспечивает параллельную работу нескольких клиентов и упрощает логику
обработки сессий.

### 3.3 Синхронизация

Используются:

- `clientsMutex_` - карта онлайн-пользователей;
- `sessionsMutex_` - список активных сессий;
- `threadsMutex_` - список worker-потоков;
- `logMutex_` - запись в лог;
- `ClientSession::writeMutex` - конкурентная отправка в один socket;
- mutex в `MessageStore` - сериализация SQL-операций;
- `std::atomic<bool>` - флаги жизненного цикла.

## 4. Клиентская часть

### 4.1 C++ клиент

`client::ClientConnection` инкапсулирует:

- подключение к серверу;
- отправку команд;
- receiver loop в отдельном потоке;
- dispatch ответов в callbacks.

Интерфейсы (CLI/Qt) используют один и тот же сетевой слой.

### 4.2 Web клиент

Браузер не может открыть raw TCP socket напрямую, поэтому используется bridge:

- браузер <-> bridge: WebSocket;
- bridge <-> сервер: TCP.

Bridge находится в `web/bridge/server.mjs` и прозрачно проксирует протокольные
строки.

Web-клиент хранит только состояние текущей сессии: выбранный чат, текст в
поле ввода, список сообщений, список чатов и строки session log. 

После входа web-клиент не выбирает первый чат автоматически. Вместо этого он
показывает пустой экран с приглашением выбрать диалог. 

Для выбора чата используется стабильный `peerId`. В личном диалоге это username
собеседника, а в группе - строка вида `group:<id>`. Это важно для frontend:
название группы может измениться, но `peerId` остается тем же.

## 5. Модель данных SQLite

Основные таблицы:

- `users`
  - учетные записи (username + salt/hash).
- `conversations`
  - уникальные пары пользователей (`user_low`, `user_high`).
- `messages`
  - сообщения личных диалогов, включая `reply_to_message_id` и
    `forward_from_message_id`.
- `conversation_reads`
  - последняя прочитанная позиция для `(conversation_id, username)`.
- `groups_chat`
  - групповые чаты, название и администратор.
- `group_members`
  - участники групп.
- `group_messages`
  - сообщения групп, включая ответы, пересылку и системные сообщения.
- `group_reads`
  - последняя прочитанная позиция в группе для конкретного пользователя.


## 6. Поток обработки сообщений

1. Клиент отправляет `send_message`.
2. Сервер валидирует пользователя и собеседника.
3. Сообщение сохраняется в SQLite.
4. Если получатель online - сервер отправляет `incoming_message`.
5. При запросе чатов сервер считает `unread_count` и возвращает в `chat_item`.
6. Когда чат открыт, клиент отправляет `mark_read`, сервер обновляет
   `conversation_reads`.

Для активного открытого чата входящее сообщение сразу помечается прочитанным:
клиент получает `incoming_message`, отображает его в текущей переписке и
отправляет `mark_read`. Для неактивного чата серверный `unread_count` остается
больше нуля, и frontend показывает красную точку в списке чатов.

Для групп используется тот же внешний поток команд, но другая таблица хранения:
`group_messages` вместо `messages` и `group_reads` вместо
`conversation_reads`. Благодаря этому личные диалоги не смешиваются с логикой
участников и администратора группы.

Ответы и пересылки строятся вокруг постоянного `message_id`. Сервер отдает его
в `send_message_result`, `incoming_message` и `history_message`, поэтому
frontend может безопасно показать цитату, открыть пересланное сообщение или
прокрутить историю к исходному сообщению.

## 7. Логи и сигналы

### 7.1 Логи

Лог-файл ведется в append-режиме и сохраняется между сессиями.

### 7.2 Сигналы

Сервер обрабатывает:

- `SIGINT`
- `SIGTERM`
- `SIGPIPE` (игнорируется)

Обработчик сигнала только выставляет флаг остановки; фактический shutdown идет
в нормальном контексте main loop.

## 8. Расширяемость

Точки расширения уже заложены:

- новые типы чатов через стабильный `chat_id`;
- треды через дополнительную ссылку на корневое сообщение;
- шифрование транспорта (TLS/OpenSSL) на сетевом уровне;
- подтверждение доставки (acked/unacked + retry queue);
- многоплатформенные фронтенды поверх текущего протокола.

## 9. Ошибки проектирования, которые были исправлены

Во время разработки несколько решений пришлось пересмотреть:

- unread-состояние сначала хотелось хранить локально в браузере, но это плохо
  работает при смене пользователей и устройств; состояние перенесено на сервер;
- автоматическое открытие первого чата после входа ломало смысл
  `unread_count`; теперь после login выбранного чата нет;
- плашка "Непрочитанные сообщения" внутри истории требовала точной границы
  сообщений, а не только количества; поэтому она временно убрана до передачи
  клиенту id последнего прочитанного сообщения;
- после добавления групп frontend сначала индексировал чаты по отображаемому
  имени `peer`, из-за чего для `group:<id>` пропадали название и кнопка
  `People`; индекс был переведен на стабильный `peerId`.
